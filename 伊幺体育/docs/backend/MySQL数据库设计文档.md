# 【体育馆运营管理系统后端】MySQL 数据库设计文档

## 商用化数据互联同步说明（2026-05-18）

- 当前可执行 schema 位于 `backend/scripts/init.sql`，首次启动 MySQL Docker volume 时自动初始化。
- 已覆盖城市、管理员、用户、门店、场地、套餐、订单、订单明细、场地占用、支付流水、退款、优惠券、活动、会员等级、积分、评价、日志和统计表。
- MySQL 是业务事实源；前端不得以本地 storage 或 mock 数据覆盖订单、支付、场地占用等事实。

## 一、数据库核心用途/设计定位

- MySQL 8 是体育馆运营管理系统的核心持久化数据库，用于保存用户、管理员、门店、场地、订单、支付、会员、优惠券、活动、评价和日志等结构化业务数据。
- 系统使用 MyBatisPlus 简化单表操作，但核心业务如预约冲突校验、订单状态流转、支付幂等仍需明确事务边界和一致性规则。
- 数据库设计必须优先保证业务正确性，再通过 Redis、索引和异步统计提升查询性能。

## 二、全局设计规范

### 2.1 通用字段

- 所有核心业务表建议包含：
  - 主键编号。
  - 创建时间。
  - 更新时间。
  - 创建人。
  - 更新人。
  - 逻辑删除标识。
  - 版本号，用于乐观锁。
- 金额字段：
  - 统一使用分为单位保存，避免浮点误差。
  - 展示时由前端转换为元。
- 状态字段：
  - 使用明确枚举值，不使用模糊数字。
  - 状态含义必须在文档和代码枚举中保持一致。
- 时间字段：
  - 订单、支付、退款、预约必须保存完整日期时间。
  - 场地业务日期与实际开始/结束时间应分开保存，支持跨天营业。

### 2.2 索引设计原则

- 登录查询字段必须建立唯一索引或普通索引。
- 订单号、支付流水号、微信支付交易号必须建立唯一索引。
- 场地时段占用表必须对场地、业务日期、开始时间、结束时间、有效状态建立冲突防护索引。
- 高频列表查询按门店、用户、订单状态、创建时间建立组合索引。
- 软删除字段如参与唯一约束，需设计为业务唯一加删除标识组合。

### 2.3 事务边界

- 创建订单、锁定场地、占用优惠券必须处于可补偿的一致性流程。
- 支付回调更新支付流水和发送订单确认消息必须保证本地幂等。
- 退款成功后更新退款流水、订单状态、优惠券恢复和积分变动必须有明确事务或补偿策略。

## 三、核心表设计

### 3.1 用户表

- 表用途：保存 C 端普通用户基础信息。
- 关键字段：
  - 用户编号。
  - 微信唯一标识。
  - 昵称。
  - 头像文件标识。
  - 手机号。
  - 用户状态。
  - 会员等级编号。
  - 积分/XX 币余额。
  - 最近使用门店编号。
- 关系：
  - 与订单表、用户优惠券表、积分流水表、评价表通过用户编号关联。
- 索引：
  - 微信唯一标识唯一索引。
  - 手机号普通索引。

### 3.2 管理员表

- 表用途：保存 B 端后台账号。
- 关键字段：
  - 管理员编号。
  - 登录账号。
  - 密码哈希。
  - 姓名。
  - 手机号。
  - 账号状态。
  - 最近登录时间。
- 关系：
  - 通过管理员角色关联表绑定角色。
  - 通过管理员门店关联表绑定可管理门店。
- 索引：
  - 登录账号唯一索引。
  - 手机号索引。

## 四、异常与边界场景

- 删除门店或场地时，不允许物理删除已有订单关联数据，应使用停用或软删除。
- 场地改名、价格修改后，不影响历史订单明细快照。
- 优惠券库存扣减失败时，订单不得继续创建为待支付。
- 支付成功但订单状态更新失败时，应通过消息重试或补偿任务修复。
- 跨天营业时段不得只用业务日期加小时数判断，否则会导致次日时段冲突错误。

## 五、AI 实现注意事项

- 不要输出 SQL 建表代码，本项目当前阶段只需要设计说明。
- 不要使用 `order` 作为未转义表名，避免和数据库关键字冲突，实际实现可使用业务前缀。
- 不要把金额保存为浮点数。
- 不要物理删除订单、支付流水、退款流水和积分流水。
- 不要只依赖 Redis 锁保证预约不冲突，MySQL 必须有兜底一致性策略。

## 六、当前 MySQL 落地信息（2026-05-18）

- 当前可执行初始化脚本为 `backend/scripts/init.sql`，由根目录 `docker-compose.yml` 挂载到 MySQL 容器 `/docker-entrypoint-initdb.d/init.sql`，首次创建 volume 时自动执行。
- 当前数据库名为 `gym_operation`，开发账号为 `gym / gym`，root 密码为 `root`，生产必须替换。
- 已落地表覆盖：`city`、`gym_store`、`venue`、`venue_package`、`venue_occupancy`、`user_profile`、`point_record`、`admin_account`、`gym_order`、`gym_order_item`、`payment_record`、`refund_request`、`coupon_template`、`activity`、`member_level`、`order_review`、`operation_log`、`daily_statistic` 等。
- 当前后端运行时主要通过 `CommercialDataRepository` 访问 MySQL，各服务共享该仓库完成查询、订单创建、支付流水、mock 支付成功、会员等级更新和统计聚合。

- `backend/scripts/README.md` 已更新为当前脚本说明；后续改表时必须同步更新 `init.sql`、本设计文档和接口联调文档。
