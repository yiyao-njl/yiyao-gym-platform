# 【体育馆运营管理系统后端】开发设计文档

## 商用化数据互联同步说明（2026-05-18）

- 当前实现已新增 `CommercialDataRepository`，核心服务通过 MySQL 读取和写入真实业务数据。
- Redis 已用于验证码与预约短锁，RabbitMQ/Nacos/nginx/Docker Compose 已纳入本地和服务器部署架构。
- `DemoDataStore` 不再作为新增运行时接口的数据源，仅可作为旧兼容或测试素材。

## 一、后端系统核心用途/产品定位

- 本后端系统是体育馆运营管理系统的业务中台和数据中枢，统一承接 C 端微信小程序、B 端管理后台以及后续第三方设备/支付平台的业务请求。
- 后端采用 SpringBoot + SpringCloud 微服务架构，围绕用户管理、门店管理、场地管理、预约开场、订单支付、会员权益、优惠活动、评价统计和后台权限管理进行模块化设计。
- 系统核心目标是支撑用户快速完成“选择门店 - 选择运动类型 - 选择场地/时段 - 下单支付 - 到店使用 - 查看订单/评价”的完整闭环，并让管理端能够配置场馆资源、处理订单、查看运营数据。
- 后端必须成为所有关键业务规则的最终裁决方。前端展示的价格、优惠、场地状态、库存和支付状态仅作为用户界面参考，最终结果以后端实时校验和返回为准。
- 系统需面向高并发预约场景设计，使用 Redis 缓存与分布式锁降低 MySQL 压力，使用 RabbitMQ 处理支付回调、订单超时、预约提醒和统计汇总等异步任务。
- 当前仓库已经在根目录 `backend/` 下落地 Spring Cloud 多模块后端骨架，包含 Maven 父工程、网关、认证、用户、场地、订单、支付、营销、会员、评价、消息、统计和公共模块。本文既描述目标设计，也记录当前骨架实现边界。

## 当前后端实现快照

- 后端工程目录为项目根目录下的 `backend/`，不是 `伊幺体育/backend/`。
- 技术版本：Spring Boot 3.3.5、Spring Cloud 2023.0.3、Java 17、Maven 多模块。
- `backend/docker-compose.yml` 已提供 MySQL 8.3、Redis 7.2、RabbitMQ 3.13 management 和 Nacos 2.3.2。
- `gym-common` 已提供统一响应 `ApiResponse`、分页 `PageResponse`、错误码、业务异常、TraceId、JWT 工具和订单/支付/退款/用户/场地状态枚举。
- `gym-gateway` 已配置 8080 端口、CORS、TraceId 过滤器、基础鉴权过滤器和基于 localhost 的服务路由。接入 Nacos 后应把路由切换为 `lb://service-name`。
- `gym-gateway` 路由需遵守 Spring Cloud Gateway Path 规则，不能使用 `/api/app/**/review` 这类 `**` 后继续追加路径的写法；评价路由当前拆为 `/api/app/orders/*/review`、`/api/app/venues/*/reviews` 和 `/api/admin/reviews/**`。
- 各业务服务已建立应用入口、`application.yml`、Controller/DTO/Service 和共享数据库访问层；当前目标是本地 Docker 可启动、三端真实数据可联调。
- 当前 Controller 已暴露认证、首页营销、用户资料、城市门店、场地时段、购物车、订单、支付、会员、评价、消息和统计等接口，核心数据通过 MySQL 返回。
- 订单与场地时段联动已切到 Redis 预约短锁和 MySQL `venue_occupancy`：创建订单时校验场地时间，预约订单占用为 `BOOKED`，到店开场占用为 `USING`。
- `POST /api/app/orders` 支持前端传入订单明细 `items`，字段包括 `venueId`、`storeId`、`packageId`、`bizDate`、`startTime`、`endTime`、`priceCent` 等；服务端会以数据库价格和占用状态为准。
- `GET /api/app/venues/{venueId}/slots` 和 `POST /api/app/reservations/check` 读取 MySQL 占用表并返回可用性。
- 管理后台位于根目录 `admin-web/`，采用 Vue3、Vite、Element Plus、Pinia、Vue Router、Axios 和 ECharts；`src/data/mock.js` 仅保留空结构占位，运行时业务数据来自后端接口。
- 仍需继续增强真实微信支付验签、订单超时关闭、优惠券库存扣减、后台更细粒度权限和审计日志。
- 前端小程序一键登录已接入后端，其他页面按首页、门店场地、购物车、订单、支付的顺序继续减少本地 mock 依赖。

## 二、主要功能详情

### 2.1 全局基础能力

- 统一 API 网关：
  - 所有 C 端和 B 端请求先进入 Spring Cloud Gateway。
  - 网关负责路由转发、跨域处理、基础限流、请求日志、Token 初步校验和异常响应包装。
  - 内部微服务不直接暴露公网入口。
- 统一响应结构：
  - 成功响应必须包含业务状态、提示信息、业务数据和请求追踪标识。
  - 失败响应必须包含错误码、错误信息、可选错误详情和请求追踪标识。
  - 分页接口必须统一返回页码、页大小、总数、总页数和列表数据。
- 统一鉴权：
  - 未登录用户允许浏览首页、门店、场地、活动等公开数据。
  - 下单、购物车、支付、会员、优惠券领取、资料修改、评价、退款等接口必须登录。
  - B 端接口必须校验管理员身份和角色权限。
- 统一状态管理：
  - 订单状态、支付状态、退款状态、场地时段状态必须由后端状态机控制。
  - 不允许前端直接传入最终状态并由后端无校验保存。
- 统一审计：
  - 管理员登录、场地配置、价格修改、订单状态修改、退款审核等关键操作必须记录操作日志。

### 2.2 用户与账号功能

- C 端普通用户：
  - 支持微信授权登录，后端通过微信登录凭证换取用户身份标识。
  - 用户资料包含头像、昵称、手机号、会员等级、积分/XX 币、优惠券数量、最近使用门店等。
  - 用户退出登录时，后端应使当前 Token 失效，前端清除本地登录态。
- B 端管理员：
  - 支持账号密码登录，密码使用 BCrypt 哈希存储。
  - 默认角色包含超级管理员、店长、员工。
  - 店长可管理所属门店的场地、订单、活动和统计数据；员工仅允许执行被授权的日常操作；超级管理员可管理全局配置。
- 登录过期：
  - 后端返回统一登录过期错误码。
  - 前端完成重新登录后可继续原操作。

### 2.3 门店与城市功能

- 城市数据：
  - 支持热门城市和 A-Z 城市列表。
  - 城市属于基础字典数据，可长期缓存。
- 门店数据：
  - 门店包含名称、地址、经纬度、联系电话、营业状态、营业时间、图片、所属城市等信息。
  - 用户可通过定位经纬度查询附近门店，也可手动按城市选择门店。
  - 门店停业、维护或删除后，不允许生成新的预约或开场订单。
- B 端配置：
  - 管理员可维护门店基础信息、营业时间、可预约天数、场地分类和场地资源。

### 2.4 场地与时段功能

- 场地分类：
  - 分类由 B 端配置，例如篮球、羽毛球、气排球、乒乓球、匹克球等。
  - 前端固定展示“全部”分类，后端返回业务分类列表。
- 场地信息：
  - 场地包含场地编号、场地名称、所属门店、运动类型、图片、基础价格、状态、可售套餐。
  - 场地状态至少包含可预约、使用中、维护中、停用。
- 时段生成：
  - 后端根据门店营业时间、预约日期、当前时间、场地占用情况和维护时间生成可用时段。
  - 到店开场模式仅返回当前时间之后可使用的营业时段。
  - 预约模式支持从今天开始往后最多 7 天，今天只展示当前时间之后的时段，未来日期展示完整营业时段。
  - 跨 24 点营业时段需按业务日期和实际开始/结束时间同时保存，避免仅按小时字符串判断。
- 时段状态：
  - `FREE` 表示可预约。
  - `BOOKED` 表示预约订单已占用但尚未到开始时间。
  - `USING` 表示到店开场订单正在使用，或预约订单已经到达开始时间。
  - `MAINTENANCE`/停用类状态由后台配置维护，不允许用户下单。
- 冲突校验：
  - 同一场地同一时间段不得被多个有效订单占用。
  - 下单前、支付前、支付回调后均需校验场地锁定与订单状态。
  - 订单取消、支付超时关闭、退款完成或管理员释放场地后，必须释放对应时段占用。

### 2.5 购物车功能

- 用户可将多个不同场地、不同日期或不同时段加入购物车后统一结算。
- 购物车项必须保存门店、场地、套餐、日期、开始时间、结束时间、时长、价格快照和创建时间。
- 加入购物车前必须校验登录态、场地状态、时段可用性和套餐有效性。
- 结算时必须重新计算价格、优惠和场地可用性，不能直接信任购物车内的历史价格。
- 对已失效、已被占用、价格变化或门店停业的购物车项，应返回明确不可结算原因。

### 2.6 订单与支付功能

- 订单类型：
  - 预约订单：用户提前选择日期与时段后支付。
  - 开场订单：用户到店或扫码后选择当前可用时段并支付。
  - 会员订单：用户开通或续费会员权益。
- 订单生成：
  - 后端创建订单时生成订单号，锁定场地时段，保存价格快照、优惠快照和用户信息快照。
  - 未支付订单设置支付超时时间，超时后自动关闭并释放场地锁。
  - 到店开场订单创建/支付成功后，关联场地时段应直接进入 `USING`。
  - 预约订单创建/支付成功后，关联场地时段先进入 `BOOKED`，当开始时间到达后订单有效使用状态和场地占用状态均应转换为 `USING`。
  - 订单列表接口和订单详情接口不能只返回静态订单类型，应按当前时间计算预约订单是否已经生效，确保前端订单 Tab 和后台订单管理看到一致状态。
- 支付处理：
  - 支付服务负责创建支付流水、调用微信支付、接收支付回调和更新支付状态。
  - 支付回调必须验签并保证幂等。
  - 支付成功后通过消息队列通知订单服务更新订单状态。
- 退款处理：
  - 用户可申请退款，后端根据订单状态、使用时间和退款规则判断是否允许。
  - 退款成功后更新退款状态，并按规则恢复优惠券或记录补偿说明。

### 2.7 会员、积分与优惠券功能

- 会员权益：
  - 会员等级由 B 端配置，包含等级名称、有效期、折扣、权益说明和升级条件。
  - 用户会员信息在下单计价时参与折扣计算，但最终折扣以后端计算为准。
- XX 币/积分：
  - 积分流水记录来源、变动值、业务单号、变动前后余额和说明。
  - 支付成功、评价完成、活动奖励等场景可产生积分。
- 优惠券：
  - 优惠券包含金额、门槛、适用门店、适用场地类型、有效期、库存、领取限制和使用状态。
  - 领取优惠券需登录并校验库存、防重复领取和活动有效期。
  - 订单支付成功后核销优惠券；订单关闭或退款时按规则恢复或作废。

### 2.8 活动与首页内容功能

- 首页轮播、热门场地、优惠活动、会员权益等内容由后端统一返回。
- 活动包含标题、图片、时间范围、规则说明、跳转目标和参与条件。
- 前端点击活动后可进入活动详情、优惠券领取页、场地详情或会员页。
- 活动上下线、过期、库存不足时，后端应在接口中返回明确状态，前端据此展示不可参与。

### 2.9 评价与统计功能

- 用户只能评价已完成且属于自己的订单。
- 评价包含评分、文字内容、图片、评价时间、管理员回复和展示状态。
- 后端需支持敏感词过滤和评价审核状态。
- 统计服务为 B 端提供订单量、收入、场地使用率、热门运动类型、评价均分、用户增长等数据。
- 高频统计可通过 RabbitMQ 异步汇总，避免每次页面访问都实时扫描订单明细。

## 三、后端技术实现要求

### 3.1 技术栈要求

- 基础框架：SpringBoot。
- 微服务框架：SpringCloud。
- API 网关：Spring Cloud Gateway。
- 服务注册与配置：Nacos。
- 鉴权安全：Spring Security + JWT + BCrypt。
- 数据库：MySQL 8。
- ORM：MyBatisPlus。
- 缓存与锁：Redis。
- 消息队列：RabbitMQ。
- 接口文档：Swagger/OpenAPI。
- 部署入口：Nginx + Gateway。
- 容器化：Docker，生产可扩展到 Kubernetes。

### 3.2 数据一致性要求

- 预约、下单、支付、退款属于核心一致性链路，必须保证状态可追溯。
- 场地时段锁定优先使用 Redis 防并发，再使用 MySQL 唯一约束或乐观锁兜底。
- 订单创建成功但支付失败或超时后，必须释放场地锁和优惠券占用。
- 支付回调可能重复到达，必须以支付流水号、订单号和回调事务号做幂等判断。
- 消息队列消费失败时必须进入重试或死信流程，不能静默丢失。

### 3.3 性能要求

- 首页、城市列表、门店列表、场地分类等基础数据应优先使用缓存。
- 场地状态、价格、优惠券库存等实时数据需在关键操作前重新校验。
- 普通页面接口响应目标控制在 500ms 内，关键下单和支付前校验目标控制在 1s 内。
- 系统需支持高峰期并发预约，压测目标参考 500 至 1000 并发用户。
- 管理端统计数据优先使用预聚合结果，避免大范围实时聚合影响交易链路。

### 3.4 安全要求

- 所有生产环境请求必须使用 HTTPS。
- 密码不得明文存储，必须使用 BCrypt。
- JWT 不保存敏感明文信息。
- 用户只能访问自己的订单、优惠券、积分、会员和评价数据。
- B 端接口必须校验管理员角色和门店数据权限。
- 金额、优惠、库存、支付结果不得由前端直接决定。
- 关键接口需防重复提交和限流，例如下单、支付、退款、领取优惠券、登录。

## 四、核心功能优化建议

- 场地状态缓存应与订单状态联动，支付成功、订单关闭、退款完成、管理员修改场地状态后及时清理或刷新缓存。
- 首页推荐可先采用后台配置和热门排序，后续再扩展个性化推荐。
- 预约流程应优先保证准确性，宁可在支付前提示“场地已被占用”，也不能出现重复售卖。
- 订单状态流转应集中在订单服务中维护，不建议分散到多个服务随意修改。
- B 端统计可采用每日定时汇总加实时补充的方式，提高统计页面打开速度。

## 五、AI 实现注意事项

- 不要修改前端页面结构来绕过后端能力缺失，后端必须提供前端需求文档中的业务数据。
- 不要把价格计算、优惠券核销、库存占用、支付结果判断放在前端。
- 不要生成明文密码、固定 Token、万能管理员账号等不安全逻辑。
- 不要直接删除订单，应使用状态变更和审计日志保留业务痕迹。
- 不要让各服务各自定义一套错误码、分页结构和响应格式。
- 不要用本地内存保存登录态、库存锁或支付状态，分布式场景必须使用 Redis/MySQL/RabbitMQ 等共享基础设施。
- 当前正式方向已切向 Redis 预约短锁 + MySQL `venue_occupancy` 占用兜底，不要再引入本地内存、TSV 文件或前端 storage 作为运行时预约事实源。
