# 【体育馆运营管理系统后端】RabbitMQ 异步消息设计文档

## 商用化数据互联同步说明（2026-05-18）

- Docker Compose 已包含 RabbitMQ management，`gym-message-service` 继续负责拓扑和消息发送封装。
- 当前订单支付主链路先保证数据库状态一致，后续应把支付成功、退款、积分、通知和统计刷新发布为 RabbitMQ 事件。

## 一、RabbitMQ 核心用途/技术定位

- RabbitMQ 用于解耦体育馆运营管理系统中的异步业务，提高支付、订单、通知、统计等链路的可靠性和响应速度。
- 交易主链路应先完成必要的数据库落库，再通过消息驱动后续处理。
- 所有关键消息必须支持幂等消费、失败重试、死信处理和消息追踪。

## 二、消息场景详情

### 2.1 支付结果通知

- 触发时机：
  - 支付服务收到微信支付成功回调并验签通过。
- 生产者：
  - 支付服务。
- 消费者：
  - 订单服务。
  - 会员积分服务。
  - 消息通知服务。
  - 统计服务。
- 消息用途：
  - 更新订单为已支付。
  - 确认场地正式占用。
  - 核销优惠券。
  - 发放积分或会员权益。
  - 发送支付成功通知。
  - 更新经营统计。
- 幂等要求：
  - 以支付单号和第三方交易号作为幂等键。
  - 重复消息不得重复发放权益或重复增加统计。

### 2.2 订单超时关闭

- 触发时机：
  - 待支付订单超过支付期限。
- 生产者：
  - 订单服务或延迟消息调度任务。
- 消费者：
  - 订单服务。
  - 预约服务。
  - 营销服务。
- 消息用途：
  - 将待支付订单关闭。
  - 释放场地预约锁。
  - 释放或恢复优惠券占用。
- 幂等要求：
  - 如果订单已支付，则超时关闭消息必须被忽略。
  - 如果订单已关闭，重复消息直接确认成功。

### 2.3 预约提醒

- 触发时机：
  - 订单支付成功后，根据预约开始时间生成提醒任务。
- 生产者：
  - 订单服务。
- 消费者：
  - 消息通知服务。
- 消息用途：
  - 在预约开始前向用户发送微信订阅消息。
  - 可提醒用户按时到店使用。
- 幂等要求：
  - 同一订单同一提醒类型只发送一次。

### 2.4 退款处理

- 触发时机：
  - 管理员审核通过退款。
  - 支付服务收到退款成功回调。
- 生产者：
  - 订单服务或支付服务。
- 消费者：
  - 支付服务。
  - 订单服务。
  - 营销服务。
  - 会员积分服务。
  - 统计服务。
- 消息用途：
  - 发起第三方退款。
  - 更新订单退款状态。
  - 按规则恢复优惠券。
  - 扣回或冲正积分。
  - 更新统计。

### 2.5 评价统计

- 触发时机：
  - 用户提交评价。
  - 管理员审核评价。
- 生产者：
  - 评价服务。
- 消费者：
  - 统计服务。
  - 场馆门店服务。
- 消息用途：
  - 更新场地平均评分。
  - 更新门店评价统计。
  - 更新 B 端评价看板。

### 2.6 运营数据统计

- 触发时机：
  - 订单支付成功。
  - 订单退款完成。
  - 订单完成。
  - 优惠券核销。
  - 会员开通。
- 生产者：
  - 订单服务、支付服务、营销服务、会员积分服务。
- 消费者：
  - 统计服务。
- 消息用途：
  - 汇总订单量、收入、场地使用率、会员增长、活动效果。

## 三、交换机与队列设计

### 3.1 交换机建议

| 交换机 | 用途 |
|---|---|
| `gym.order.exchange` | 订单创建、取消、超时、完成相关消息 |
| `gym.payment.exchange` | 支付成功、支付失败、退款成功相关消息 |
| `gym.marketing.exchange` | 优惠券领取、核销、活动参与相关消息 |
| `gym.member.exchange` | 会员开通、积分变动相关消息 |
| `gym.review.exchange` | 评价提交、审核、回复相关消息 |
| `gym.stat.exchange` | 统计汇总相关消息 |
| `gym.notify.exchange` | 微信订阅消息、系统通知相关消息 |

### 3.2 队列建议

| 队列 | 消费者 | 用途 |
|---|---|---|
| `order.payment.success.queue` | 订单服务 | 支付成功确认订单 |
| `order.timeout.close.queue` | 订单服务 | 超时关闭订单 |
| `reservation.release.queue` | 预约服务 | 释放预约锁 |
| `coupon.writeoff.queue` | 营销服务 | 优惠券核销或恢复 |
| `member.activate.queue` | 会员积分服务 | 开通会员和积分发放 |
| `payment.refund.queue` | 支付服务 | 发起第三方退款 |
| `notify.user.queue` | 消息通知服务 | 用户通知 |
| `stat.aggregate.queue` | 统计服务 | 运营数据汇总 |
| `review.stat.queue` | 统计服务 | 评价统计 |

### 3.3 路由键建议

| 路由键 | 事件 |
|---|---|
| `order.created` | 订单创建 |
| `order.closed.timeout` | 订单超时关闭 |
| `order.cancelled` | 订单取消 |
| `payment.success` | 支付成功 |
| `payment.failed` | 支付失败 |
| `refund.requested` | 退款申请 |
| `refund.success` | 退款成功 |
| `coupon.claimed` | 优惠券领取 |
| `coupon.used` | 优惠券核销 |
| `member.activated` | 会员开通 |
| `review.created` | 评价提交 |
| `stat.order.changed` | 订单统计变更 |

## 四、消息体字段规范

- 通用字段：
  - 消息编号。
  - 事件类型。
  - 业务单号。
  - 用户编号。
  - 门店编号。
  - 发生时间。
  - 生产服务。
  - 追踪标识。
  - 重试次数。
- 支付成功消息字段：
  - 订单号。
  - 支付单号。
  - 第三方交易号。
  - 支付金额。
  - 支付时间。
- 订单超时消息字段：
  - 订单号。
  - 支付超时时间。
  - 需要释放的场地占用编号列表。
- 退款成功消息字段：
  - 订单号。
  - 退款单号。
  - 退款金额。
  - 第三方退款号。
  - 退款完成时间。

## 五、重试、死信与幂等

### 5.1 重试策略

- 消费失败后允许有限次数重试。
- 重试间隔应逐步拉长，避免瞬时故障导致消息风暴。
- 外部依赖故障如微信通知失败，可进入专门补偿队列。

### 5.2 死信队列

- 达到最大重试次数后进入死信队列。
- 死信消息必须保留业务单号、失败原因和最后异常摘要。
- 运维或补偿任务可人工或自动重新投递死信消息。

### 5.3 幂等消费

- 消费端必须先检查消息编号或业务幂等键是否已处理。
- 处理成功后记录消费结果。
- 重复消息直接确认，不得再次执行业务副作用。

## 六、异常与边界场景

- 支付成功消息发送失败时，支付服务必须记录待补偿事件。
- 订单服务消费支付成功消息失败时，不得丢弃消息，应重试或进入死信。
- 消息顺序不可靠时，消费端必须根据数据库当前状态判断是否可执行。
- 退款成功先于退款申请状态更新到达时，应通过订单号查询权威状态后处理。

## 七、AI 实现注意事项

- 不要把 RabbitMQ 当作数据库，消息只负责事件传递。
- 不要消费消息后不做幂等记录。
- 不要在消息中放入密码、支付密钥或完整用户隐私信息。
- 不要因为通知发送失败而回滚已成功支付的订单。
- 不要让统计消息阻塞订单、支付主链路。

## 八、当前 RabbitMQ 落地信息（2026-05-18）

- 根目录 `docker-compose.yml` 使用 `rabbitmq:3.12-management-alpine`，容器名 `gym-rabbitmq`，端口 `5672` 和管理端 `15672`，开发账号 `gym / gym`。
- `gym-message-service` 当前通过 `RabbitTopologyConfig` 声明两个 TopicExchange：`gym.order.exchange` 和 `gym.payment.exchange`。
- 当前声明队列包括 `order.payment.success.queue` 和 `order.timeout.close.queue`。
- 当前绑定关系：`payment.success` 绑定到 `order.payment.success.queue`；`order.closed.timeout` 绑定到 `order.timeout.close.queue`。
- `MessagePublishService` 当前负责发送消息，`/internal/messages/mock-payment-success` 可发布一条 `PAYMENT_SUCCESS` 测试事件到 `gym.payment.exchange`。
- 目前支付服务 mock 成功主要通过 MySQL 同步更新订单和支付流水，RabbitMQ 拓扑已经可用，但支付成功事件驱动订单状态机、死信、重试、消费幂等仍需继续补齐。
