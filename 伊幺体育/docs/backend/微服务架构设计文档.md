# 【体育馆运营管理系统后端】微服务架构设计文档

## 商用化数据互联同步说明（2026-05-18）

- 保留现有 Spring Cloud 多模块边界，网关统一 `/api/**` 入口。
- Docker Compose 本地默认通过容器服务名代理各微服务，`application-nacos.yml` 保留 `lb://service-name` 服务发现路由方案。
- 服务器迁移时沿用同一套镜像、环境变量和 nginx 反向代理配置。

## 一、微服务核心用途/架构定位

- 微服务架构用于拆分体育馆运营管理系统中高耦合、高并发、可独立扩展的业务能力。
- 系统以 SpringBoot 为单服务基础，以 SpringCloud 负责服务治理，以 Gateway 作为统一入口，以 Nacos 作为服务注册与配置中心。
- 架构目标是让用户、场地、订单、支付、营销、统计等模块能够独立开发、独立部署、独立扩容，同时保持统一鉴权、统一日志和统一接口规范。

## 二、服务划分详情

### 2.1 网关服务

- 服务职责：
  - 统一接收 C 端小程序和 B 端管理后台请求。
  - 根据路径转发到对应业务服务。
  - 处理跨域、限流、请求追踪、基础鉴权、灰度路由和异常包装。
- 路由建议：
  - `/api/auth/**` 转发认证服务。
  - `/api/users/**` 转发用户服务。
  - `/api/stores/**`、`/api/venues/**` 转发场馆门店服务。
  - `/api/reservations/**` 转发场地预约服务。
  - `/api/orders/**` 转发订单服务。
  - `/api/payments/**` 转发支付服务。
  - `/api/marketing/**` 转发营销服务。
  - `/api/admin/**` 转发后台管理相关服务。
- 实现要求：
  - 网关只做入口控制，不写复杂业务逻辑。
  - 网关鉴权失败时返回统一错误码。
  - 网关必须透传请求追踪标识到后续服务。

### 2.2 认证服务

- 服务职责：
  - 处理微信小程序登录、B 端账号密码登录、Token 签发、Token 刷新、退出登录。
  - 管理登录态缓存、黑名单 Token、验证码校验和登录安全策略。
- 对外能力：
  - 小程序登录。
  - 管理端登录。
  - 刷新 Token。
  - 退出登录。
  - 查询当前登录用户身份。
- 依赖关系：
  - 读取用户服务或管理员账号数据。
  - 使用 Redis 存储登录态、刷新 Token、验证码和黑名单。

### 2.3 用户服务

- 服务职责：
  - 管理 C 端用户资料、手机号、头像、昵称、会员摘要、积分余额和用户偏好。
  - 维护用户最近使用门店、常用运动类型、用户基础画像。
- 对外能力：
  - 查询用户基础资料。
  - 修改用户资料。
  - 查询我的页面聚合信息。
  - 查询用户资产摘要。
- 实现要求：
  - 用户隐私字段必须按需返回。
  - 用户资料修改必须校验本人身份。

### 2.4 场馆门店服务

- 服务职责：
  - 管理城市、门店、场地分类、场地、图片、营业时间、维护时间和场地套餐。
  - 为 C 端提供门店选择、场地列表、场地详情和时段状态。
  - 为 B 端提供场馆资源配置能力。
- 对外能力：
  - 查询热门城市和 A-Z 城市。
  - 按定位或城市查询门店。
  - 查询门店场地分类。
  - 查询场地列表和详情。
  - 查询指定日期的场地时段状态。
- 实现要求：
  - 基础配置变更后清理相关 Redis 缓存。
  - 营业时间、维护时间和订单占用必须共同参与时段生成。

### 2.5 场地预约服务

- 服务职责：
  - 管理场地时段可用性、预约锁、到店开场锁、扫码开场校验。
  - 处理下单前的时段占用检查和临时锁定。
- 对外能力：
  - 校验场地时段可用性。
  - 创建预约锁。
  - 释放预约锁。
  - 扫码开场校验。
- 实现要求：
  - Redis 锁用于快速防并发，MySQL 唯一约束或乐观锁用于最终兜底。
  - 预约锁必须设置过期时间，避免异常导致永久占用。
  - 支付成功后临时锁转为正式占用。

### 2.6 订单服务

- 服务职责：
  - 管理预约订单、开场订单、会员订单、订单明细、订单状态流转、取消订单和退款申请。
  - 作为业务状态机中心，控制订单从创建到完成的完整生命周期。
- 对外能力：
  - 创建订单。
  - 查询订单列表。
  - 查询订单详情。
  - 取消订单。
  - 申请退款。
  - 支付成功后确认订单。
  - 订单超时关闭。
- 实现要求：
  - 订单服务不得直接信任前端金额。
  - 订单状态变更必须幂等。
  - 所有状态变更必须记录时间和来源。

### 2.7 支付服务

- 服务职责：
  - 管理支付流水、微信支付下单、支付回调、退款请求、退款回调。
  - 将支付结果通过 RabbitMQ 通知订单服务。
- 对外能力：
  - 创建支付单。
  - 查询支付状态。
  - 接收支付回调。
  - 发起退款。
  - 接收退款回调。
- 实现要求：
  - 支付回调必须验签。
  - 支付结果必须根据第三方交易号和订单号做幂等。
  - 支付服务只确认资金状态，订单业务状态由订单服务处理。

### 2.8 营销服务

- 服务职责：
  - 管理优惠券、活动、首页轮播、热门推荐和活动参与记录。
  - 提供优惠券领取、可用优惠券查询和优惠试算能力。
- 对外能力：
  - 查询首页营销内容。
  - 查询活动详情。
  - 领取优惠券。
  - 查询用户优惠券。
  - 订单计价时提供可用优惠和核销结果。
- 实现要求：
  - 优惠券库存必须防超发。
  - 优惠券核销必须与订单支付状态联动。

### 2.9 会员积分服务

- 服务职责：
  - 管理会员等级、会员有效期、积分/XX 币余额和积分流水。
  - 支持会员开通、续费、升级和权益查询。
- 对外能力：
  - 查询会员权益。
  - 创建会员订单所需权益快照。
  - 支付成功后开通或续费会员。
  - 记录积分变动流水。
- 实现要求：
  - 积分变动必须记录业务来源，禁止只改余额不写流水。
  - 会员折扣需要参与订单计价，但以订单服务最终计算结果为准。

### 2.10 评价服务

- 服务职责：
  - 管理订单评价、评分、评论图片、敏感词过滤、管理员回复和评价展示。
- 对外能力：
  - 提交评价。
  - 查询场地评价。
  - 查询我的评价。
  - B 端回复或隐藏评价。
- 实现要求：
  - 仅已完成订单允许评价。
  - 同一订单默认只允许评价一次。

### 2.11 统计服务

- 服务职责：
  - 为 B 端提供收入统计、订单统计、场地使用率、会员增长、优惠券核销和评价统计。
- 对外能力：
  - 查询经营看板。
  - 查询收入趋势。
  - 查询场地使用率。
  - 查询活动效果。
- 实现要求：
  - 大部分统计通过异步消息或定时任务预聚合。
  - 交易链路不得依赖统计服务成功。

### 2.12 文件服务

- 服务职责：
  - 管理场地图片、活动图片、用户头像、评价图片等文件元数据。
  - 对接微信云开发存储或对象存储。
- 对外能力：
  - 生成上传凭证。
  - 保存文件记录。
  - 获取临时访问链接。
- 实现要求：
  - 业务表保存文件标识，不直接保存大文件内容。
  - 文件访问链接应支持过期机制。

### 2.13 消息服务

- 服务职责：
  - 封装 RabbitMQ 消息发送、消费、重试、死信和消息日志。
  - 负责微信订阅消息、订单提醒、支付通知等通知类任务。
- 实现要求：
  - 关键消息必须可追踪。
  - 消费端必须幂等。

## 三、服务通信与治理要求

### 3.1 服务注册与发现

- 所有业务服务启动后注册到 Nacos。
- 网关通过服务名发现下游服务。
- 服务间调用优先使用内部服务名，不使用公网地址。
- 配置按环境隔离，例如开发、测试、生产。

### 3.2 服务间调用

- 同步调用用于强一致或即时反馈场景，例如订单创建时查询场地、用户、优惠信息。
- 异步消息用于最终一致场景，例如支付成功通知、统计汇总、消息提醒。
- 服务间调用必须设置超时、重试边界和降级策略。

### 3.3 限流与熔断

- 网关层对登录、下单、支付、领取优惠券等接口做基础限流。
- 服务层对第三方支付、文件存储、短信或订阅消息等外部依赖做熔断降级。
- 降级时必须返回明确提示，不能返回成功假象。

### 3.4 日志与链路追踪

- 每个请求必须生成或透传请求追踪标识。
- 业务日志至少记录用户编号、订单号、门店编号、接口名、耗时、结果。
- 支付、退款、订单状态变更、管理员操作必须记录审计日志。

## 四、异常与边界场景

- Nacos 不可用时，已启动服务应尽量保持已有配置运行，新服务启动失败需告警。
- Redis 不可用时，登录、缓存和预约锁能力会受影响，系统应限制下单等高风险操作。
- RabbitMQ 不可用时，交易主链路可先落库，但待发送消息必须有补偿机制。
- 支付服务回调延迟时，前端查询订单应返回“支付处理中”，并触发后端主动查询支付状态。
- 某个微服务异常时，网关不得暴露内部堆栈。

## 五、AI 实现注意事项

- 不要把所有业务写进网关服务。
- 不要让支付服务直接修改所有订单业务细节，应通过订单服务状态机处理。
- 不要让统计服务影响下单、支付等核心链路。
- 不要跨服务直接访问彼此数据库，必须通过接口或消息交互。
- 不要在多个服务中重复定义不一致的订单状态、支付状态和错误码。

## 六、当前模块落地信息（2026-05-18）

- `gym-gateway` 当前使用 Spring Cloud Gateway，路由已经覆盖小程序 `/api/app/**`、后台 `/api/admin/**` 和内部 `/internal/messages/**`。本地默认转发 `http://localhost:8101-8110`，Docker Compose 通过 `GYM_AUTH_URI`、`GYM_ORDER_URI` 等环境变量改为容器服务名。
- `gym-common` 当前承担跨服务公共能力：`ApiResponse`、`PageResponse`、`ErrorCode`、`BizException`、TraceId、JWT 工具、状态枚举和 `CommercialDataRepository`。新增服务能力应优先复用这些统一结构。
- `gym-auth-service` 当前已落地小程序微信登录、短信验证码登录、管理员登录、Token 刷新和退出接口。管理员账号读 MySQL，短信验证码写 Redis，JWT 仍使用开发密钥。
- `gym-venue-service` 当前已落地城市、门店、场地、场地类型、套餐、场地时段和预约校验接口，数据来自 MySQL。
- `gym-order-service` 当前已落地购物车示例接口、订单创建、订单列表/详情、取消、退款申请、后台退款审核和到店核销接口。创建订单时使用 Redis 20 秒短锁，并通过 MySQL `venue_occupancy` 做占用兜底。
- `gym-payment-service` 当前已落地支付单创建、支付状态查询、mock 支付成功、微信支付回调预留、云支付回调预留、退款回调预留和后台支付列表/汇总接口。
- `gym-message-service` 当前已落地 RabbitMQ 拓扑：`gym.order.exchange`、`gym.payment.exchange`、`order.payment.success.queue`、`order.timeout.close.queue`，并提供 `/internal/messages/mock-payment-success` 测试发布接口。
- `gym-statistics-service` 当前通过 MySQL 聚合看板数据，供后台首页和统计页使用。
- Nacos 当前作为基础设施保留，`application-nacos.yml` 提供 `lb://service-name` 方案；当前完整 Docker 链路默认仍使用网关环境变量直连服务容器。
