# 【体育馆运营管理系统后端】容器化部署与运维设计文档

## 商用化数据互联同步说明（2026-05-18）

- 根目录已新增 `docker-compose.yml`，统一编排 MySQL、Redis、RabbitMQ、Nacos、nginx、管理后台和后端服务。
- `backend/Dockerfile` 按 Maven 模块构建微服务镜像，`admin-web/Dockerfile` 使用 Node 构建并由 nginx 托管。
- 服务器迁移时复制 Compose、`.env` 和 nginx 配置，替换域名、密钥和数据卷路径即可。

## 一、部署核心用途/运维定位

- 容器化部署用于让体育馆运营管理系统后端微服务具备可复制、可扩展、易回滚的运行环境。
- 开发和测试环境可使用 Docker Compose 组织基础服务；生产环境建议使用 Kubernetes 管理多实例微服务。
- Nginx 作为外部反向代理入口，Gateway 作为业务 API 网关，后端业务服务只在内网暴露。

## 二、整体部署拓扑

### 2.1 外部访问层

- Nginx：
  - 负责 HTTPS 终止。
  - 负责静态资源代理。
  - 负责将 API 请求转发到 Gateway。
  - 可配置基础负载均衡和访问日志。
- 域名建议：
  - C 端小程序 API 域名。
  - B 端管理后台 API 域名。
  - 静态资源域名。

### 2.2 网关层

- Gateway：
  - 至少部署 2 个实例。
  - 接收 Nginx 转发的业务请求。
  - 通过 Nacos 发现下游服务。
  - 处理限流、鉴权、路由和统一异常。

### 2.3 业务服务层

- 建议容器化服务：
  - 认证服务。
  - 用户服务。
  - 场馆门店服务。
  - 场地预约服务。
  - 订单服务。
  - 支付服务。
  - 营销服务。
  - 会员积分服务。
  - 评价服务。
  - 统计服务。
  - 文件服务。
  - 消息服务。
- 扩容优先级：
  - 高峰期优先扩容 Gateway、场地预约服务、订单服务、支付服务。
  - 统计服务、评价服务可按资源情况较低优先级扩容。

### 2.4 基础设施层

- MySQL：
  - 保存核心业务数据。
  - 生产环境建议主从或云数据库高可用。
  - 必须配置定期备份和恢复演练。
- Redis：
  - 保存缓存、锁和登录态。
  - 生产环境建议哨兵或集群模式。
- RabbitMQ：
  - 保存异步消息。
  - 生产环境建议镜像队列或仲裁队列。
- Nacos：
  - 服务注册与配置中心。
  - 生产环境至少多节点部署。

## 三、Docker 镜像设计要求

- 每个微服务单独构建镜像。
- 镜像命名应包含服务名和版本号。
- 镜像中不写入生产数据库密码、支付密钥或云存储密钥。
- 配置通过环境变量、配置中心或挂载密钥注入。
- 镜像启动后必须暴露健康检查端点。
- 同一版本镜像在测试和生产环境保持一致，通过配置区分环境。

## 四、Docker Compose 开发环境思路

- 适用场景：
  - 本地开发。
  - 接口联调。
  - 基础功能测试。
- 建议包含：
  - MySQL。
  - Redis。
  - RabbitMQ。
  - Nacos。
  - Gateway。
  - 少量核心业务服务。
- 注意事项：
  - 开发环境可简化高可用配置。
  - 不应使用生产真实密钥。
  - 本地数据库可使用模拟数据或脱敏数据。

## 五、Kubernetes 生产部署思路

- 每个微服务使用独立工作负载。
- Gateway、订单、预约、支付等关键服务配置多副本。
- 使用服务发现暴露集群内访问地址。
- 使用配置对象管理非敏感配置。
- 使用密钥对象管理数据库密码、JWT 密钥、支付密钥等敏感配置。
- 使用健康检查实现异常实例自动剔除。
- 使用水平扩缩容策略应对高峰预约。
- 使用滚动发布降低上线风险。

## 六、配置中心与环境变量

### 6.1 配置中心内容

- 服务端口。
- 数据库连接信息。
- Redis 连接信息。
- RabbitMQ 连接信息。
- Nacos 命名空间。
- JWT 有效期。
- 订单支付超时时间。
- 最大可预约天数。
- 网关限流规则。
- 第三方支付回调地址。

### 6.2 敏感配置

- JWT 签名密钥。
- 微信小程序密钥。
- 微信支付商户密钥。
- 数据库密码。
- Redis 密码。
- 对象存储访问密钥。
- 生产环境敏感配置不得写入代码仓库。

## 七、日志、监控与告警

### 7.1 日志

- 网关访问日志：
  - 请求路径、用户标识、客户端类型、耗时、状态码、追踪标识。
- 业务服务日志：
  - 关键业务编号、状态变更、异常摘要、追踪标识。
- 支付日志：
  - 支付单号、订单号、第三方交易号、回调状态、验签结果。
- 审计日志：
  - 管理员操作、退款审核、价格修改、场地停用等。

### 7.2 监控指标

- 服务存活状态。
- 接口响应时间。
- 接口错误率。
- Gateway 请求量。
- MySQL 连接数和慢查询。
- Redis 命中率和内存使用。
- RabbitMQ 队列堆积。
- 订单创建成功率。
- 支付回调成功率。
- 订单超时关闭数量。

### 7.3 告警场景

- 支付回调失败率升高。
- 订单支付成功但状态未更新。
- RabbitMQ 队列大量堆积。
- Redis 不可用或锁异常。
- MySQL 慢查询持续增加。
- Gateway 5xx 错误率升高。
- 某个门店场地状态长时间不刷新。

## 八、备份与恢复

- MySQL：
  - 每日全量备份。
  - 高频业务可增加增量备份。
  - 定期进行恢复演练。
- Redis：
  - 登录态和锁可重建，缓存无需强恢复。
  - 优惠券库存等关键缓存必须能从 MySQL 补偿恢复。
- RabbitMQ：
  - 关键队列需持久化。
  - 死信队列需定期巡检。
- 文件存储：
  - 图片和上传文件需要对象存储生命周期与备份策略。

## 九、发布与回滚

- 发布前：
  - 通过接口自动化测试。
  - 确认数据库变更兼容旧版本。
  - 确认配置中心已更新。
- 发布中：
  - 优先滚动发布非核心服务。
  - 订单、支付、预约服务低峰发布。
  - 观察错误率、支付回调和订单创建指标。
- 回滚：
  - 镜像版本可回退。
  - 配置变更可回退。
  - 数据库结构变更必须提前设计兼容方案，避免无法回滚。

## 十、AI 实现注意事项

- 不要在部署文档中输出 Dockerfile、Compose 或 Kubernetes YAML，本阶段只需要设计说明。
- 不要把生产密钥写入配置样例。
- 不要让业务服务直接暴露公网。
- 不要只部署单实例 Gateway、Redis、RabbitMQ 或 Nacos 到生产环境。
- 不要缺少健康检查和日志追踪，否则后续排障会非常困难。

## 十一、当前容器化落地信息（2026-05-18）

- 当前完整本地链路以根目录 `docker-compose.yml` 为准，服务包括 MySQL、Redis、RabbitMQ、Nacos、10 个后端业务服务、`gym-gateway`、`admin-web` 和 nginx。
- MySQL 使用 `mysql:8.3`，挂载 `backend/scripts/init.sql`；Redis 使用 `redis:7-alpine`；RabbitMQ 使用 `rabbitmq:3.12-management-alpine`；Nacos 使用 `nacos/nacos-server:v2.3.2`。
- 后端镜像统一使用 `backend/Dockerfile`，通过 build arg `MODULE` 构建指定 Maven 模块。
- 后台镜像使用 `admin-web/Dockerfile`，nginx 配置在 `admin-web/nginx.conf`；根目录反向代理配置在 `deploy/nginx/default.conf`。
- 根 nginx 暴露 `80` 端口，`/api/` 转发到 `gym-gateway:8080`，其他路径转发到 `admin-web:80`。
- `.env.example` 当前包含数据库、Redis、RabbitMQ、Nacos、JWT 和 `PAYMENT_MOCK_ENABLED` 的开发配置；生产部署必须替换所有默认密码和密钥。
- `docker-compose.local-images.yml` 当前只是本地镜像覆盖占位，完整运行仍以根目录 `docker-compose.yml` 为准。
