# 【体育馆运营管理系统后端】Redis 缓存与并发控制设计文档

## 商用化数据互联同步说明（2026-05-18）

- 当前实现已使用 Redis 保存短信验证码，并在创建订单时对场地日期和时段加短锁。
- Redis 锁用于降低并发冲突，MySQL `venue_occupancy` 唯一约束和重叠校验仍是最终兜底。
- 后续商用化应补充锁续期、超时释放、限流和热点场地缓存。

## 一、Redis 核心用途/技术定位

- Redis 用于提升体育馆运营管理系统的高频读取性能，并承担登录态、验证码、临时支付状态、购物车摘要、场地时段锁、优惠券库存防超发等并发控制职责。
- Redis 不是最终数据源，核心业务数据仍以 MySQL 为准。
- 下单、支付、退款等关键链路必须采用 Redis 快速防并发 + MySQL 持久化约束的双重保护。

## 二、缓存场景详情

### 2.1 登录与会话缓存

- 缓存内容：
  - C 端用户刷新 Token。
  - B 端管理员刷新 Token。
  - 访问 Token 黑名单。
  - 登录态版本。
  - 登录验证码或短信验证码。
- Key 建议：
  - `auth:refresh:app:{userId}:{deviceId}`。
  - `auth:refresh:admin:{adminId}:{deviceId}`。
  - `auth:blacklist:{tokenId}`。
  - `auth:version:{userType}:{userId}`。
  - `auth:captcha:{scene}:{target}`。
- TTL 建议：
  - 刷新 Token：7 至 30 天。
  - 黑名单 Token：与访问 Token 剩余有效期一致。
  - 验证码：5 分钟。

### 2.2 用户与我的页面缓存

- 缓存内容：
  - 用户资料摘要。
  - 会员等级摘要。
  - 积分/XX 币余额摘要。
  - 优惠券数量摘要。
- Key 建议：
  - `user:summary:{userId}`。
  - `user:asset:{userId}`。
- TTL 建议：
  - 5 至 15 分钟。
- 更新策略：
  - 用户修改资料、会员变更、积分变动、优惠券领取或核销后主动删除缓存。

### 2.3 城市、门店与场地基础缓存

- 缓存内容：
  - 热门城市。
  - A-Z 城市列表。
  - 城市门店列表。
  - 门店详情。
  - 门店场地分类。
  - 场地详情。
- Key 建议：
  - `city:hot`。
  - `city:az`。
  - `store:list:city:{cityId}`。
  - `store:detail:{storeId}`。
  - `venue:type:list:{storeId}`。
  - `venue:detail:{venueId}`。
- TTL 建议：
  - 城市数据：12 至 24 小时。
  - 门店和场地基础数据：10 至 60 分钟。
- 更新策略：
  - B 端修改城市、门店、场地分类、场地信息后清理对应缓存。

### 2.4 场地状态缓存

- 缓存内容：
  - 指定门店、日期、场地分类下的场地列表状态。
  - 指定场地、日期的时段状态。
- Key 建议：
  - `venue:status:list:{storeId}:{typeId}:{bizDate}:{mode}`。
  - `venue:slot:{venueId}:{bizDate}`。
- TTL 建议：
  - 30 秒至 3 分钟。
- 更新策略：
  - 订单创建、支付成功、订单关闭、退款完成、管理员维护场地后删除相关缓存。
  - 支付前必须绕过或刷新缓存，重新校验 MySQL 和锁状态。

### 2.5 购物车缓存

- 缓存内容：
  - 用户购物车数量。
  - 用户已勾选购物车项摘要。
- Key 建议：
  - `cart:count:{userId}`。
  - `cart:checked:{userId}`。
- TTL 建议：
  - 10 至 30 分钟。
- 更新策略：
  - 加入、删除、勾选、取消勾选购物车项后主动更新或删除缓存。

### 2.6 优惠券库存缓存

- 缓存内容：
  - 优惠券剩余库存。
  - 用户领取次数。
- Key 建议：
  - `coupon:stock:{couponId}`。
  - `coupon:claim:user:{couponId}:{userId}`。
- TTL 建议：
  - 活动结束时间之后自动过期。
- 更新策略：
  - 领取时先在 Redis 扣减，成功后写 MySQL。
  - MySQL 写入失败时必须回补库存或进入补偿任务。

### 2.7 支付临时状态缓存

- 缓存内容：
  - 支付单处理状态。
  - 支付轮询结果。
  - 防重复支付标识。
- Key 建议：
  - `payment:status:{paymentNo}`。
  - `payment:lock:{orderNo}`。
- TTL 建议：
  - 支付状态：30 分钟至 2 小时。
  - 支付锁：根据支付超时时间设置。

## 三、并发控制设计

### 3.1 预约锁

- 适用场景：
  - 用户下单前锁定场地时段。
  - 购物车结算前批量锁定多个场地时段。
- Key 建议：
  - `lock:venue:{venueId}:{bizDate}:{startTime}:{endTime}`。
- 锁内容：
  - 用户编号。
  - 订单号或临时业务号。
  - 锁定时间。
  - 过期时间。
- TTL 建议：
  - 与订单支付超时时间一致，建议 10 至 15 分钟。
- 要求：
  - 加锁成功后才能创建待支付订单。
  - 订单关闭、支付失败、超时取消后释放锁。
  - 支付成功后锁转为 MySQL 正式占用，不依赖 Redis 永久保存。

### 3.2 优惠券库存锁

- 适用场景：
  - 多用户同时领取同一优惠券。
  - 下单时临时占用用户优惠券。
- 要求：
  - 领取时校验用户领取次数。
  - 库存扣减成功不代表最终成功，必须写入用户优惠券记录。
  - 订单创建后优惠券进入占用状态，支付成功后进入已使用状态，订单取消后恢复可用或按规则作废。

### 3.3 防重复提交

- 适用接口：
  - 创建订单。
  - 发起支付。
  - 申请退款。
  - 领取优惠券。
  - 提交评价。
- Key 建议：
  - `repeat:{scene}:{userId}:{requestHash}`。
- TTL 建议：
  - 5 秒至 60 秒，根据业务风险确定。
- 要求：
  - 同一用户短时间重复提交相同业务请求，应返回上一次处理结果或明确提示重复操作。

### 3.4 支付幂等锁

- 适用场景：
  - 用户重复点击支付。
  - 微信支付回调重复通知。
- Key 建议：
  - `idem:payment:create:{orderNo}`。
  - `idem:payment:callback:{transactionId}`。
- 要求：
  - 已存在有效支付单时直接返回原支付参数或支付状态。
  - 已处理过的支付回调不得重复更新订单、重复发消息或重复发放权益。

### 3.5 热点数据保护

- 热点数据：
  - 首页内容。
  - 热门城市。
  - 热门门店。
  - 热门场地。
  - 热门优惠券。
- 保护策略：
  - 设置随机 TTL，避免同一时间大量过期。
  - 使用互斥锁或逻辑过期防止缓存击穿。
  - 对不存在的数据缓存短时间空值，防止缓存穿透。

## 四、缓存更新与一致性要求

- 基础数据采用 Cache Aside 策略：先查缓存，未命中查 MySQL，写入缓存。
- 修改基础数据时，先更新 MySQL，再删除缓存。
- 核心状态数据不长期依赖缓存，关键操作必须访问 MySQL 或调用权威服务校验。
- 消息异步更新缓存失败时，应允许下一次读取自动回源修复。
- 缓存删除失败必须记录日志，必要时进入补偿任务。

## 五、异常与边界场景

- Redis 不可用时：
  - 登录刷新、预约下单、领取优惠券等高风险操作应降级为不可用或严格走数据库锁。
  - 首页、城市、门店等可回源 MySQL，但需限流保护。
- 缓存与数据库不一致时：
  - 订单、支付、场地占用以 MySQL 为准。
  - 前端显示可订但支付前校验不可订时，后端应返回场地不可用提示。
- 锁过期但支付回调成功：
  - 订单服务必须根据订单状态和 MySQL 占用记录进行补偿判断。

## 六、AI 实现注意事项

- 不要把 Redis 当成订单、支付、积分等核心数据的唯一存储。
- 不要使用没有过期时间的业务锁。
- 不要在释放锁时删除不属于当前业务请求的锁。
- 不要只靠前端按钮禁用来防重复提交。
- 不要在缓存中保存密码、微信密钥、支付密钥等敏感信息。

## 七、当前 Redis 落地信息（2026-05-18）

- 根目录 `docker-compose.yml` 使用 `redis:7-alpine`，容器名 `gym-redis`，本地端口 `6379`，后端通过 `GYM_REDIS_HOST`、`GYM_REDIS_PORT` 配置连接。
- `gym-auth-service` 当前使用 `StringRedisTemplate` 保存短信验证码，key 为 `gym:sms:{phone}`，开发期验证码为 `123456`，过期时间 5 分钟。
- `gym-order-service` 当前使用 `StringRedisTemplate` 做场地预约短锁，key 为 `gym:venue:lock:{venueId}:{bizDate}:{startTime}:{endTime}`，过期时间 20 秒。
- 订单创建流程会先校验参数，再逐个获取 Redis 短锁，随后调用 `CommercialDataRepository.createOrder()` 写 MySQL 订单、订单明细和 `venue_occupancy`，最后释放已获取的短锁。
- 当前短锁 value 仍是固定 `locked`，后续生产增强应改为请求唯一 token，释放锁时校验 token，避免误删其他请求锁。
- 当前 Redis 仅用于验证码和并发短锁，不保存订单、支付、积分等核心事实；核心事实仍以 MySQL 为准。
