# 【体育馆运营管理系统后端】测试验收与 AI 实现约束文档

## 商用化数据互联同步说明（2026-05-18）

- 验收重点调整为三端真实数据互联：小程序登录/下单/支付后，后台用户、订单、支付流水和统计同步可见。
- 并发预约必须验证同一场地同一日期同一时段只能成功一单。
- Docker 本地启动、服务重启数据不丢失、nginx 代理和 MySQL volume 持久化均纳入验收。

## 一、测试验收核心用途/质量定位

- 本文档用于约束 AI 编程软件在实现后端系统时的质量目标、测试范围和禁止行为。
- 后端系统必须通过功能测试、接口测试、并发测试、安全测试、支付回调测试、缓存一致性测试和部署健康检查。
- 验收重点不是“接口能返回数据”，而是核心业务链路在真实并发、支付回调、登录过期和异常场景下仍然正确。

## 二、功能测试场景

### 2.1 用户与登录

- 微信小程序新用户首次登录后自动创建用户。
- 已有用户再次登录后返回原用户资料。
- 登录过期后访问下单接口返回统一未登录错误。
- 退出登录后旧 Token 不得继续访问受保护接口。
- 管理员账号密码正确时可登录。
- 管理员密码错误、账号禁用、角色禁用时不得登录。

### 2.2 首页与公开数据

- 未登录用户可访问首页、活动、门店、场地基础信息。
- 首页聚合接口返回轮播、热门场地、活动和可选用户摘要。
- 城市列表返回热门城市和 A-Z 城市结构。
- 门店列表支持定位查询和城市查询。
- 场地分类固定支持前端展示“全部”，业务分类由后端返回。

### 2.3 开场与预约

- 到店开场模式只返回当前时间之后可用营业时段。
- 预约模式最多返回今天起 7 天日期范围。
- 今天只展示当前时间之后时段，未来日期展示完整营业时段。
- 场地维护中、停用、门店停业时不得下单。
- 跨天营业时段能正确展示和校验。
- 同一场地同一时段不得被重复预约。

### 2.4 购物车

- 登录用户可加入购物车。
- 未登录用户加入购物车返回登录提示。
- 购物车项能勾选、取消勾选和删除。
- 结算时后端重新校验价格、优惠和时段可用性。
- 已被占用或价格变化的购物车项返回明确不可结算原因。

### 2.5 订单与支付

- 正常预约下单生成待支付订单。
- 待支付订单能创建支付单。
- 支付成功回调后订单状态更新为已支付或预约已生效。
- 支付失败时订单保持可重新支付或关闭状态。
- 支付超时后订单关闭并释放场地锁。
- 重复支付回调不会重复更新订单或重复发放权益。
- 已支付订单不能直接取消，必须走退款流程。

### 2.6 会员、优惠券、活动

- 用户可领取有效且有库存的优惠券。
- 用户不能重复领取超过限制。
- 过期、下线、库存不足的优惠券不能领取。
- 下单时只返回适用当前门店、场地类型和金额门槛的优惠券。
- 支付成功后优惠券变为已使用。
- 订单关闭后优惠券按规则恢复。
- 会员支付成功后会员等级和有效期正确更新。

### 2.7 评价与统计

- 用户只能评价自己的已完成订单。
- 同一订单不能重复评价。
- 评价提交后可在场地评价列表中按审核状态展示。
- 管理员可回复或隐藏评价。
- 支付成功、退款完成、评价提交后统计数据最终能更新。

### 2.8 B 端管理

- 超级管理员可查看全局数据。
- 店长只能查看和管理所属门店数据。
- 员工只能访问授权功能。
- 管理员修改场地、价格、营业时间后，C 端相关缓存及时刷新。
- 退款审核记录操作日志。

## 三、接口测试要求

- 所有接口返回统一响应结构。
- 所有分页接口返回统一分页字段。
- 参数缺失、类型错误、非法枚举值必须返回参数错误。
- 无数据列表返回空数组，不返回系统异常。
- 业务冲突返回明确错误码，例如场地不可用、订单已过期、优惠券不可用。
- Swagger/OpenAPI 文档必须覆盖 C 端和 B 端主要接口。
- 接口字段命名在文档、后端、前端中保持一致。

## 四、并发测试要求

### 4.1 预约并发

- 测试目标：
  - 500 至 1000 并发用户同时预约同一热门场地时段。
- 期望结果：
  - 只有一个或符合库存规则的订单成功锁定。
  - 其他请求返回场地不可用或业务冲突。
  - 不出现重复售卖。

### 4.2 优惠券并发

- 测试目标：
  - 多用户同时领取有限库存优惠券。
- 期望结果：
  - 成功领取数量不超过库存。
  - 同一用户不超过限领数量。
  - Redis 与 MySQL 库存最终一致。

### 4.3 支付回调并发

- 测试目标：
  - 同一支付回调重复请求多次。
- 期望结果：
  - 支付流水只成功处理一次。
  - 订单状态只流转一次。
  - 会员、积分、优惠券、统计不重复处理。

## 五、安全测试要求

- 未登录访问受保护接口必须失败。
- 普通用户修改请求中的用户编号后不能访问他人数据。
- 店长访问非所属门店订单必须失败。
- 员工访问未授权管理功能必须失败。
- 密码不得明文返回或保存。
- JWT 篡改后必须校验失败。
- SQL 注入、非法排序字段、超大分页参数必须被拦截或限制。
- 支付回调验签失败不得更新支付状态。
- 文件上传必须限制类型、大小和访问权限。

## 六、缓存一致性测试要求

- 修改门店信息后，C 端门店详情缓存刷新。
- 修改场地状态后，场地列表和详情状态刷新。
- 支付成功后，场地时段缓存刷新。
- 订单超时关闭后，场地时段重新可用。
- 领取优惠券后，库存缓存与 MySQL 最终一致。
- Redis 缓存清理失败时，系统可通过 TTL 或补偿任务恢复一致。

## 七、消息队列测试要求

- 支付成功消息能被订单服务消费。
- 订单超时消息能关闭待支付订单。
- 消费失败后消息进入重试。
- 重试超过限制后进入死信队列。
- 死信消息保留业务单号和失败原因。
- 重复消息不会造成重复业务副作用。

## 八、部署验收要求

- 所有微服务健康检查可访问。
- Gateway 能发现并转发到下游服务。
- Nacos 中服务实例状态正确。
- MySQL、Redis、RabbitMQ 连接正常。
- 日志中包含请求追踪标识。
- 支付回调地址可公网访问且经过 HTTPS。
- 生产环境敏感配置不出现在代码仓库和普通日志中。

## 九、AI 实现硬性约束

- 不改前端页面结构来掩盖后端接口缺失。
- 不绕过后端业务校验。
- 不把价格、库存、优惠、支付状态逻辑放到前端决定。
- 不明文保存密码。
- 不跳过 JWT 鉴权和 B 端权限校验。
- 不跳过支付回调验签。
- 不跳过支付、退款、消息消费幂等。
- 不物理删除订单、支付流水、退款流水、积分流水和操作日志。
- 不使用本地内存保存分布式锁、登录态或订单状态。
- 不让各微服务直接访问彼此数据库。
- 不在文档或配置中写入真实密钥。

## 十、验收通过标准

- 文档中的 C 端核心页面均有对应后端接口或业务能力。
- 文档中的核心数据均有 MySQL 持久化设计。
- 文档中的高频和高并发场景均有 Redis 策略。
- 文档中的异步场景均有 RabbitMQ 事件设计。
- 文档中的交易链路均包含幂等和异常处理。
- 文档不包含可执行代码块、SQL 建表语句、Dockerfile 或 Kubernetes YAML。
- AI 编程软件可以依据本组文档开始后端项目实现，无需再猜测服务边界、接口范围和核心业务规则。

## 十一、当前测试验收同步信息（2026-05-18）

- 后端基础验证命令仍建议使用 `mvn test`；若只验证单模块，可使用 `mvn -pl gym-auth-service -am test` 这类 Maven 模块命令。
- 完整联调验收以根目录 `docker compose up -d --build` 启动三端链路后进行，入口包括 `http://localhost/` 后台和 `http://localhost/api/app/home` 网关接口。
- 当前必须重点验收的真实数据链路：小程序一键登录写入用户、场地预约校验读 MySQL 占用、订单创建写 `gym_order`/`gym_order_item`/`venue_occupancy`、mock 支付成功写 `payment_record` 并更新订单、后台看板能看到订单支付统计。
- 当前后台 `src/data/mock.js` 不再提供假业务数据，验收时接口失败应暴露为空态或错误提示。
- 当前仍未完成生产级能力包括真实微信支付验签、支付查单、退款状态机、订单超时关闭任务、RabbitMQ 消费幂等和细粒度权限；测试报告中应明确这些属于后续增强项。
- AI 后续改代码时，必须同步更新对应模块文档，特别是接口路径、表结构、Redis key、RabbitMQ exchange/queue、Docker 环境变量和验收命令。
